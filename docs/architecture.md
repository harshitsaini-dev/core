# Core — Architecture

> Zero-knowledge password, secret and environment manager.
> Live: `core.harshitsaini.in` · Self-hostable by anyone.

---

## 1. Guiding principle

**The server is untrusted.**

Core is designed so that the person who owns the code, the database, the server
and the production `.env` file still cannot read a single stored password or
secret value. Every design decision below follows from that one constraint.

Concretely, the server only ever sees:

- opaque ciphertext blobs
- an authentication verifier derived from — but not reversible to — the master password
- blind-index HMAC tags used for equality lookups
- non-sensitive routing metadata (row ids, timestamps, ownership)

The server never sees: master password, master key, account key, item titles,
usernames, URLs, folder names, project names, `.env` keys or `.env` values.

## 3. Cryptographic design

### 3.1 Key hierarchy

| Key | Derived / generated by | Lives where | Purpose |
|---|---|---|---|
| Master Password | human | the user's head | root of trust, never transmitted |
| Root Key | `Argon2id(mp, userSalt)` | transient, wiped immediately | the single expensive derivation |
| Master Key | `HKDF(root, info="core.enc.v1")` | browser memory only | wraps the Account Key |
| Auth Key | `HKDF(root, info="core.auth.v1")` | sent to server per login | proves identity |
| Auth Verifier | `HMAC-SHA256(serverPepper, authKey)` | D1 `users.auth_verifier` | server-side compare target |
| Account Key | 32 random bytes at signup | browser memory; wrapped blob at rest | encrypts every vault item |
| Item Key | per-item 32 random bytes (large items, attachments) | wrapped by Account Key | limits blast radius, enables sharing |
| ECDH Key Pair | P-256, generated client-side at signup | public key in D1, private key wrapped by Account Key | one-time share links, future multi-user |
| Device Key | non-extractable WebCrypto key, per device | IndexedDB handle only | encrypts the offline cache |

**Why the Account Key indirection matters:** changing the master password only
re-wraps one 32-byte key. Zero re-encryption of the vault, zero bulk server
round trips.

### 3.2 Parameters

- **KDF** — Argon2id, `m = 64 MiB, t = 3, p = 1`, tuned so one browser
  derivation costs roughly 500–800 ms. Params are stored per user in D1 so they
  can be raised later without breaking existing accounts.
- **One derivation, two keys** — Argon2id runs *once*. Its 32-byte output is
  split by HKDF-Expand into the Auth Key and the Master Key using distinct
  `info` strings. Running Argon2id twice would double every unlock for no gain:
  the security of both keys already rests on that single computation. See
  ADR-011.
- **Salt** — 16 random bytes per user, returned by an unauthenticated
  `POST /api/auth/prelogin`. That endpoint must respond in constant time and
  return a deterministic fake salt for unknown emails, otherwise it becomes a
  user-enumeration oracle.
- **Cipher** — AES-256-GCM, fresh 12-byte IV per encryption, never reused. The
  GCM auth tag gives tamper detection for free.
- **Verifier** — `HMAC-SHA256(pepper, authKey)`, not a second Argon2id pass.
  The Auth Key is already the output of a memory-hard derivation, so an attacker
  holding the database still pays the full Argon2id cost per password guess;
  repeating that work server-side would add nothing and would hand anyone a
  cheap way to exhaust the Worker's CPU budget. See ADR-012.
- **Pepper** — a server-side secret (`AUTH_PEPPER`) mixed into the verifier
  only. Deliberately *not* part of the data-encryption path: if the pepper
  leaks the vault is still unreadable, and if the database leaks without the
  pepper an offline attack on the verifier cannot even start.
- **Libraries** — native `crypto.subtle` for AES / ECDH / HKDF / HMAC. Argon2id
  via a pinned WASM build (`hash-wasm`), since WebCrypto has no Argon2. That is
  the only cryptographic dependency in the project.

### 3.3 Encrypted record shape

Every sensitive column stores one self-describing string:

```
v1.<base64url iv>.<base64url ciphertext+tag>
```

The version prefix lets the cipher be migrated later without a flag day.

Sensitive wrappers additionally pass a fixed **AAD** string (for example
`core.account-key.v1`). The AAD is authenticated but not encrypted, so a
ciphertext cannot be lifted out of one column and replayed into another by a
hostile server — it simply fails to decrypt.

### 3.4 Blind index — lookups without disclosure

For the few fields that need server-side equality matching (resolving a share
token, deduplicating a URL), the client also sends
`HMAC-SHA256(blindIndexKey, normalize(value))` truncated to 16 bytes, where
`blindIndexKey = HKDF(accountKey, info = "core.blind-index.v1")`. The server can run
`WHERE blind_index = ?` but cannot invert it.

Everything else — fuzzy search, filtering, sorting — happens **client-side over
the decrypted in-memory index**. That is precisely why the whole vault syncs to
the device.

## 4. Repository layout (pnpm monorepo)

```
core/
+- apps/
|  +- web/                     Next.js App Router - UI + Route Handlers
|     +- app/
|     |  +- (auth)/            login, signup, unlock
|     |  +- (vault)/           vault, folders, item detail
|     |  +- (env)/             projects, environments, .env editor
|     |  +- settings/          security, devices, audit log, import/export
|     |  +- api/               route handlers (edge runtime)
|     +- lib/                  client stores, hooks, sync engine
|     +- public/               manifest.json, icons, service worker
+- packages/
|  +- crypto/                  KDF, AES-GCM, ECDH, blind index
|  +- db/                      Drizzle schema, migrations, D1 client
|  +- ui/                      terminal-themed primitives
|  +- shared/                  zod schemas, types, constants
+- docs/
+- .github/workflows/
+- wrangler.toml
```

**Hard rule:** `packages/crypto` has no network access, no React and no
Node-only APIs. It stays pure, isomorphic and fully unit-testable — that is what
makes the zero-knowledge claim auditable by a stranger.

## 5. Data model (D1 / SQLite)

Columns marked **[E]** hold ciphertext and never plaintext.

```
users
  id, email_blind_index, email_enc[E], auth_verifier, kdf_salt, kdf_params_json,
  account_key_wrapped[E], public_key, private_key_wrapped[E],
  created_at, updated_at

folders
  id, user_id, parent_id, name_enc[E], color, sort_order, created_at

vault_items
  id, user_id, folder_id, type ('login'|'note'|'card'|'identity'|'ssh'),
  data_enc[E],           -- entire item JSON: title, username, password, url,
                         -- custom fields, TOTP secret, recovery codes
  url_blind_index, favorite, last_used_at,
  created_at, updated_at, deleted_at

item_versions
  id, item_id, data_enc[E], created_at          -- history + rollback

projects
  id, user_id, name_enc[E], color, created_at

environments
  id, project_id, name_enc[E]                   -- dev / staging / prod

env_vars
  id, environment_id, key_enc[E], value_enc[E], note_enc[E], updated_at

env_var_versions
  id, env_var_id, key_enc[E], value_enc[E], created_at   -- diff viewer source

attachments
  id, item_id, blob_key, item_key_wrapped[E], size, mime_enc[E], created_at

sessions
  id, user_id, device_id, token_hash, expires_at, revoked_at

devices
  id, user_id, label_enc[E], ua_hash, first_seen_ip_hash, trusted, last_seen_at

audit_log
  id, user_id, event, ip_hash, geo_country, ua_hash, created_at

shares
  id, sender_id, payload_enc[E], token_blind_index, max_views,
  view_count, expires_at
```

Even `folders.name` and `env_vars.key` are encrypted — the operator must not
learn which bank you use or that a project holds a `STRIPE_SECRET_KEY`.

## 6. Sync engine

Core is offline-first. The client is the source of truth for plaintext; D1 is a
dumb encrypted replica.

1. On unlock, pull every row changed since `lastSyncCursor`.
2. Decrypt into an in-memory index (Zustand) and persist the ciphertext to Dexie.
3. Mutations write to Dexie immediately (optimistic UI) and enqueue an outbox op.
4. The outbox drains to `POST /api/vault/sync`; failures retry with backoff.
5. Conflicts resolve last-write-wins per field, with the losing value preserved
   in `item_versions` so nothing is ever silently destroyed.

Offline mode is fully read-write; writes queue until connectivity returns.

## 7. Defence in depth beyond the crypto

| Layer | Control |
|---|---|
| Transport | HTTPS only, HSTS with preload, no mixed content |
| Headers | strict nonce-based CSP (no `unsafe-inline`), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, COOP/COEP |
| Supply chain | SRI on external assets, pinned lockfile, Dependabot, `pnpm audit` in CI |
| Auth endpoints | Turnstile, IP rate limit, account lockout, progressive delay, constant-time compare |
| Session | short-lived token in `HttpOnly; Secure; SameSite=Strict` cookie plus rotating refresh |
| Client memory | keys held as non-extractable `CryptoKey` wherever possible; raw byte buffers explicitly zeroed on lock |
| Storage | IndexedDB holds ciphertext only, wrapped by a per-device non-extractable key |
| UI | auto-lock on inactivity, clipboard auto-clear, panic button, blur-all mode |

## 9. Explicit non-goals for v1

- **Browser-extension autofill** — a separate project with its own threat model.
- **Team / organisation vaults** — the ECDH plumbing makes this additive later,
  but it is not v1 scope.
- **Administrator password reset** — impossible by design, and that is the
  entire point. Losing the master password without the Emergency Kit means
  losing the vault.
- **Server-side search over plaintext** — never.
